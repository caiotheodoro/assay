| W2a | First question was whether a task-safety filter was worth the coverage it costs. | `InspectAdapter` fabricates a `TaskState` carrying only `output.completion`; a scorer reading `state.store` gets `{}` and returns a score, silently | **The filter is a correctness requirement, not an optimisation, and this is the whole design of `sweep.py`.** For `match`/`pattern`/`includes` the fabricated state is exactly faithful. For a scorer reading a sandbox, a tool transcript, or the store it is not faithful *and does not raise* — it returns a degenerate score computed from an empty world, and every such score looks like a finding. Sweeping without the filter would emit fabricated defect reports against real published benchmarks, which is worse for this project than finding nothing. |

| W2e | Multiple-choice tasks would all have failed the anchor: `choice()` reads `state.choices`, which the `multiple_choice` *solver* populates, and a bare `"A"` as the completion marks nothing. | `arc_easy`, `arc_challenge`, `hellaswag`, `commonsense_qa`, `gpqa_diamond` all anchor 25/25 under `protocol=multiple_choice`, 0/25 under `raw` | **Replayed the solver's own step rather than simulating it.** The completion is formatted the way `inspect_ai`'s `SINGLE_ANSWER_TEMPLATE` asks, then `inspect_ai`'s own `parse_answers` and `set_choices_based_on_generated_response` are called — the `Choices` object the scorer reads is built by the library, not by this file. `multiple_correct` is read out of the solver's closure and the task is refused if it cannot be read: a multi-answer task scored as single-answer would mark every gold wrong and look like a broken benchmark. |
| W2f | Bounded dataset materialisation with `signal.alarm`. | `docvqa` took the HF cache past **18 GB** with a 240 s budget nominally in force; the sweep had to be killed by hand | **It does not work, and the fix is a process boundary.** A factory pulling a multi-gigabyte multimodal dataset sits inside `datasets`' C-level download and never reaches a bytecode boundary where the handler could run. Each task now sweeps in its own process *group*, killed outright on expiry — `datasets` spawns workers, so killing the parent alone leaves them downloading. Isolation is worth more than the timeout: a task that segfaults costs one row instead of the sweep, and a sweep that died partway while reporting its prefix as the whole picture is the silent-gap failure this module exists to prevent. |
| W2g | Ran the sweep and triaged the hits by hand. **`paws` is a real, unplanted, critical defect in a published eval.** It scores with `includes()` — a case-insensitive *substring* test — against the targets `"Yes"` and `"No"`. | `uv run --extra adapters --extra sweep pytest tests/test_wild_findings.py -q`; `results/wild_sweep.json` task `paws` | **Confirmed, from the eval's own code with Assay out of the loop.** Every one of `"I cannot determine the answer."`, `"I don't know"`, `"Not sure"`, `"None of the above"` is marked CORRECT whenever the target is `"No"` — each contains the substring in *cannot*, *know*, *not*, *none*. The looseness is one-sided, which is worse than symmetric: it makes the No class (4464 of 8000 items) systematically easier for any model that hedges. The strongest form is a single constant string: `"yesno"` contains both labels and is scored correct against **8000/8000** items. This is the WebArena substring-match failure from the README's own table, live in a benchmark shipping today. |
| W2h | Assay found the weaker half of that and missed the stronger. | `results/wild_sweep.json`: 16 of 25 sampled `paws` items report `REWARD_HACKABLE`, `exploit_policy=trivial:always_escalate`, `exploit_gap=1.0`; `tests/test_wild_findings.py::TestWhatAssayItselfFound` | **Recorded as a test so the gap cannot quietly close in the write-up.** The scripted Challenger's repertoire *is* the adapter's trivial policies, and none of them names both labels at once, so the 100% exploit came from hand triage. `TRIVIAL_FLOOR_BREACH` also, correctly, did not fire: the escalate policy averages 0.6 against gold's 1.0, and the probe's aggregate rule is that a trivial policy must *tie or beat* the best real one. The probe is right and too coarse to see this, which is a different thing from being wrong. |
| W2i | Checked whether the same hazard was mishandled elsewhere in the swept scope. | `tests/test_wild_findings.py::TestBoolqAnchoredPattern` | **`boolq` is the contrast that makes the `paws` finding legible, and a narrower leak of its own.** Same two short labels, but scored `pattern(r"(Yes\|No).?\Z")`. Anchoring at the end is a real mitigation: most refusals come back NOANSWER instead of credited, and no constant string satisfies both targets. It still leaks — `.?` admits exactly one trailing character and *know* is *no* plus *w*, so `"I don't know"` is CORRECT on every No-targeted item. | W2j | Whether a subsampled audit of these evals is even repeatable. | two identical `paws()` calls returned sample ids `['7531','6916','818',…]` and `['7622','1046','5001',…]`; `paws(shuffle=False)` returns `['1','2','3',…]` both times | **It is not, and this is not specific to the audit.** `paws` and `boolq` both default to `shuffle=True` with no seed, so any run using `--limit N` — the standard way to run a subset — draws different items each time and two limited runs are not comparable.
